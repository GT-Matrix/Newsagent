# 2026-07-06 重构提交总结

这份文档说明 `refactor/modnews-service-architecture` 分支上，进入中文 commit 阶段后，尤其是 2026-07-06 这批高频提交，实际在做什么。

重点不是简单罗列 commit message，而是解释这些提交分别在推进哪一层架构改造，以及它们之间的关系。

## 总体结论

2026-07-06 这批提交，核心上同时推进了六件事：

1. 把 pipeline 从“任务列表”推进成“注册式 step graph + callback graph”
2. 把 classify 从“大函数 + 内部并发”推进成“外层节点 / 内层子任务 / 统一 checkpoint”模型
3. 把 event queue 补成真正可观察、可恢复、可表达 blocked/waiting/retry 的运行时
4. 把 repository / runtime config / extraction / repair 这些大模块拆职责
5. 把前端和 CLI 需要的读模型补齐，让新架构可以被外部操作和观察
6. 把 compat / legacy 壳标出来，逐步封口旧路径

所以这批提交不是在做“改名字”或者“收拢入口”这种表面整理，而是在给新架构补运行时语义、状态语义、读模型语义和节点装配边界。

这组提交实际做了四层改造：

### 1. 拆 classify 内部职责

把原来混在一起的内容拆开：

- runtime 解析
- LLM client 构造
- retriever 构造
- state input 构造
- step sequence 组装
- observer
- result snapshot
- checkpoint 持久化

这样后面迁移单个节点时，不需要碰整个 classify 过程。

### 2. 给 classify 子任务建立标准元数据

批子任务开始统一具备：

- 标准 task type
- 标准 queue task type
- 标准 batch metadata
- 标准 executor 注册方式
- 明确的父任务继承语义

这让 embedding、relevance、clustered extraction、clustered merge 可以被前端和读模型统一理解。

### 3. 固化 classify 的 checkpoint / result / stage 语义

昨天这一批把 classify 结果从“最后写几个 json 文件”，逐步推进成：

- step result 有稳定结构
- next stage 有稳定含义
- checkpoint meta 有统一字段
- run artifact / fixed output / checkpoint output 边界清晰
- 从 run checkpoint 恢复路径稳定

这部分直接支撑了后续“让 report 接 `classification_progress.json` 作为标准输入”的方向。

### 4. 开始真正迁移第一个节点

最后两条是昨天重构最实质的一步：

- `6a0a581` 先把 classify 首节点内部批任务运行时抽出来
- `a5fe1b4` 再把 `clustered_event_extraction` 外层改成回调驱动

当前这个节点已经从“一次调用跑完整个节点”，改成：

1. 父任务第一次运行，注册 embedding 子任务
2. 父任务 blocked
3. embedding 子任务完成，通过回调让父任务 retry
4. 父任务再次运行，注册 extraction 子任务
5. 父任务再次 blocked
6. extraction 子任务完成，通过回调让父任务 retry
7. 父任务汇总结果，写 checkpoint，任务结束

这一步不是 façade，而是 classify 节点迁移真正开始落地。

## 九、当前仍然没完成的部分

虽然昨天这批提交已经把骨架搭得很深，但还没有完全收尾。

当前仍然存在的主要差距：

- `clustered_event_merge` 还没有迁成和 extraction 一样的 callback-driven 节点
- report 还没有彻底按“节点收回调再注册任务”的风格收平
- extraction / repair 里仍有一些重模块需要继续压薄
- 外部前端 `modnews_webUI` 还没有系统性对齐这套新读模型和节点语义

也就是说，昨天的工作不是终点，而是把项目从“结构上能继续做”推进到了“第一批真实节点开始按新模型迁移”。
